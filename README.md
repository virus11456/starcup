# 星杯傳說 Online · 正式擴充引擎整合

以 Next.js、React、Three.js 與 Supabase 實作的非官方多人卡牌遊戲。部署目標為 Vercel。

## 正式擴充模式 `/full`

新增自架的無名杯 GPL-3.0 規則引擎，固定上游 commit 與 SHA-256，於建置時取得，不嵌入第三方網站。十週年 37 位、異端業火 5 位、神子創臨 6 位、終末禱鑄 5 位及特典 15 位，共 68 位角色、455 項技能／資源標記已接入；三／四版 16 個舊版變體只在另選版本時開放。每一角色的技能指向可執行定義，並附角色圖片和操作提示。

牌庫還原 150 張：五系攻擊各 21、暗滅 6、聖光 11、聖盾 10、中毒 6、虛弱 6、魔彈 6；保留屬性、派系及獨有技標記。支援引擎的治療、能量、提煉、角色資源、技能回應和追加行動。Three.js 負責立體桌面、金屬星杯、座位光環和粒子，無 WebGL 時仍可玩平面牌局。

依使用者要求排除破曉、BOSS、trick 與農暴食等同人註冊。正式爆食少女依百科牌面及 FAQ 另行實作五項技能；三秒原則測試包括展示／暗棄、實體／轉換、延後結算、一次回收多張及牌移離棄牌堆的情況。**68 位角色仍需逐項 FAQ 與交互技能驗收，不能宣稱完整原作驗收完成。** 原引擎文字仍以簡體為主，外層介面使用繁體。

**此模式目前為本機對 AI，未接入 Supabase 多人同步。** 原核心版多人 API 與完整事件引擎不相容；連線版本仍需獨立整合。已移除上游公共大廳與戰績上傳，CSP 限制引擎網路請求只送本站。未借用上游服務或憑證。

引擎來源、授權和修改見 `vendor/noname/NOTICE.md`、`vendor/noname/LICENSE`。重建及驗證：

```bash
npm run prepare:engine
npm run test:engine
npm test
npm run typecheck
npm run build
```

首次建置會下載約 114 MB 的固定來源包；後續使用校驗過的本機快取。不要提交產生的 `public/engine`、快取或環境變數。`public/full-engine/catalog.json` 是可追蹤的角色／牌庫清單。下面段落描述原本的核心測試模式，與正式擴充模式分開。

## 已實作

- 可搜尋的星杯規則字典：21 則規則問答，支援自然問題關鍵字與繁簡體，提供來源連結及測試版差異；沒有依據時不生成裁定。
- 11 種基礎卡牌原圖、手牌與圖鑑放大檢視；4 位角色的肖像與完整技能參考卡。選牌時按相關時機顯示技能提醒，未實作的技能明確標示不可施放。
- 桌面為主的對戰排版、下方扇形手牌與右側行動面板。可用行動與目標由同一規則引擎驗證，包含不可使用原因，不會洩漏其他玩家手牌。

- Three.js 3D 金屬星杯、圓桌、紅藍棋子、牌堆、粒子與燈光；OrbitControls 旋轉／縮放，Raycaster 點選目標。手機可使用觸控，亦保留可鍵盤操作的玩家按鈕。
- 4／6／8 人房間、8 位邀請碼、公開／邀請房、準備、房主開局、聊天與電腦補位。
- 六種攻擊與五種法術、應戰、聖光／聖盾、魔彈傳遞、中毒、虛弱、手動棄牌、購買、星杯合成與兩種勝利條件。
- 伺服器驗證每個動作；每個回應只傳回自己的手牌。對手手牌、牌庫順序、會話憑證不會傳至瀏覽器。
- 房間狀態存於 Postgres，以 revision 比對更新防止同時寫入覆蓋。前端每 1.8 秒同步，非 WebSocket。
- 90 秒回合期限，逾時代打；原瀏覽器 Cookie 可恢復席位。房間閒置 24 小時後拒絕加入。
- 不依賴後端的本機單人練習模式。離開練習會結束該局，練習不能多人連線。

## 此版本的界線

這不是完整原版規則的復刻。角色技能、治療、提煉能量、BP、技能優先序與擴充裁定尚未實作。選擇角色目前只變更圖片與教學提醒，不改變遊戲結算。已整理風之劍聖、狂戰士、聖女與神射手，共 19 項技能參考。

測試牌組共 150 張：火／水／風／地／雷攻擊各 18 張；暗滅、聖光、中毒、虛弱、聖盾、魔彈各 10 張。尚未還原法術屬性、卡面技能標記及原版逐張配比。座位採紅藍交錯，合成消耗最早取得的三個星石，戰績區只剩一格時購買優先補寶石。

對戰沒有每回合自動補牌。魔彈與攻擊皆可被聖光或聖盾抵擋；聖盾不會剝奪先應戰／聖光的選擇。無法行動時可依伺服器判斷重抽手牌。

## 本機開發

Node.js 22.13+，建議 Node.js 24。使用已提交的 pnpm lockfile：

```bash
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env.local
pnpm dev
```

沒有資料庫設定時仍可使用「單人練習」。線上房間需要以下伺服器環境變數，**均不可加 NEXT*PUBLIC* 前綴**：

| 變數                       | 用途                                  |
| -------------------------- | ------------------------------------- |
| `SUPABASE_URL`             | Supabase 專案 URL                     |
| `SUPABASE_PUBLISHABLE_KEY` | Publishable API key                   |
| `GRAIL_SERVER_SECRET`      | 自行產生的至少 32-byte 隨機伺服器密鑰 |

## 資料庫部署

1. 產生強隨機 `GRAIL_SERVER_SECRET`，安全地放入環境變數。
2. 計算該密鑰 UTF-8 字串的 SHA-256 hex digest；以 digest 替換 `database/schema.sql` 的 `SERVER_KEY_SHA256` 佔位文字。
3. 在專屬 Supabase 專案套用 SQL。密鑰原文不得放進 SQL 或 Git。
4. 表格 `grail_rooms` 啟用 RLS。只有持有自訂伺服器 header 的請求可讀寫；單獨持有 publishable key 的瀏覽器不能存取房間資料。

這個設計不使用 Supabase Auth，也不需要 service-role key。玩家身分由 256-bit HttpOnly、SameSite=Lax 的會話 Cookie 識別；資料庫內只保存其 SHA-256 摘要。換裝置或清除 Cookie 無法恢復原席位。Vercel Function 持有伺服器密鑰並執行所有規則，不接受客戶端提供的新遊戲狀態。

RLS 是資料層的伺服器認證邊界；玩家授權由 `app/api/game/route.ts` 與 `lib/game.ts` 檢查。資料庫不公開原始表格給玩家。HTTP 修改請求拒絕跨來源操作，回應禁止快取。

## Vercel

1. 建立 GitHub repository 並推送此專案。
2. Vercel 匯入 repository，Framework 選 **Next.js**，Node.js 選 **24.x**。
3. 加入上表三個環境變數（production／preview／development），確認資料庫 RLS digest 相符。
4. 部署。`vercel.json` 指定東京 `hnd1`，與 Supabase 東京區域一致。
5. 以不同瀏覽器／裝置開啟網址，建立房間並用邀請碼加入。驗證出牌同步與自己的手牌可見性。

Vercel Function 不保存進程內對戰狀態，因此重新啟動或不同 instance 仍會讀取同一個資料庫。自動代打由在線玩家輪詢觸發，無人在線時牌局不會持續消耗背景運算。首次輪詢會接續逾時的動作。

## 維運限制

- 目前為同好測試用途，尚未加入帳號、跨裝置席位恢復、觀戰、戰績排行、持久聊天室、管理後台或規模化防濫用機制。
- 每個來源每小時最多建立 5 間房；此限制尚不是分散式原子計數，正式大規模公開前需加強。
- 閒置房間會在 API 層過期，但資料列不會自動刪除；正式營運時應新增定時清理策略。
- 3D 無法初始化時會提示使用平面玩家按鈕，規則與牌局仍可操作。音效、正式角色模型尚未加入。
