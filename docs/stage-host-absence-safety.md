# 多人對戰：房主失聯時隔離過期操作

2026-10-26，Cloudflare 遷移後續本機階段。本項是對已部署 `cloudflare-migration` 的防護增量；在集中發布前**沒有部署到正式 Cloudflare**，不改 `main`／Vercel，也不寫入正式房間。

## 現有能力與尚未完成的遷移

- 4／6／8 人房、邀請碼、Durable Objects＋SQLite 中繼及 WebSocket 休眠持久化已在 Cloudflare 運行；此前累計 10 場多人、10 場單人自然結算驗收。
- 雲端儲存的是房間／座位／訊息進度，**不是原生引擎的完整事件執行狀態**。房主瀏覽器關閉或重新整理後，原本對局的事件堆疊、牌庫／技能 continuation 無法由目前 Durable Object 安全重建。
- 房主原分頁暫時離線後重新連上可恢復同步；真正關閉分頁後，**仍不能由其他玩家或 Cloudflare 無損接手**。不能據此認定 Vercel 可刪除。

## 本階段的具體防護

1. 若開始的牌局已超過 60 秒沒有房主同步（對應服務端的 `hostAlive=false`），客人的原生牌局立即進入等待恢復狀態，**不再送出過期的選擇**，也不把缺頁的訊息片段套用到舊畫面；等待室不受此邏輯影響。
2. 客人看到可理解的文字：等房主回到**原分頁**；如已關閉分頁，目前不能接手，可「離開」另開新局。當相同房主真的回來，客人透過原座位重新初始化原生畫面，不重複使用舊選擇介面。
3. Durable Object 在已開始的牌局確認房主失聯後，驗證並標記客人發出的訊息 ID，但**不存入待交付收件匣**。連線錯失回覆後的相同訊息重試也不會讓舊選擇落入房主稍後復原的 inbox；此保護涵蓋 HTTP 與 WebSocket 的共用同步核心。
4. 等待原房主期間，客人的 HTTP fallback 與 WebSocket 心跳由一般頻率放緩至每 30 秒一次，仍在房間 60 秒的客人存活窗之內，以免不必要地消耗 Durable Objects 同步請求；房間尚未開始時保留原頻率。

## 驗證／發布邊界

- 新增原生 adapter、HTTP fallback、房間同步與 workerd SQLite／WebSocket 休眠重開的回歸測試，涵蓋過期選擇拒收、ID 重試去重、房主恢復、等待室不誤判。
- 完整 `npm run verify:local` exit 0（應用測試、原生引擎／adapter、10 項本機 Cloudflare runtime、Vinext 建置與 TypeScript），另 64 項建置後 HTTP／權限／邀請邊界檢查全數通過；`git diff --check` 通過。
- 只在本機測試資料上跑驗證，不把 fixture 通關數字算成新增自然結算場次。
- 此防護旨在限制失聯期間的錯誤操作，**並未交付房主關頁遷移、雲端權威引擎或主機接管**。

## 下一階段

1. 先設計可驗證的原生事件完整續行／確定性重播，或可持續運行原引擎的房主架構；不能只存一般 JSON 牌面快照。需要處理魔彈鏈、插入回合、動態技能、逾時競態與雙房主互斥。
2. 完成手機／桌面實機斷網、原房主恢復、客人重新初始化與完整自然結算驗收，檢查 Cloudflare 的錯誤、連線和 SQLite 使用量。
3. 與 `main`／Vercel 進行版本和路由依賴比對，完成實際站點切換驗收後，才能宣布 Vercel 可移除。
